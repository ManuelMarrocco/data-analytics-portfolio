DATA QUALITY JOURNAL — CONTEXT AND STARTING POINT

ITA:
Questo Data Quality Journal nasce come fase preliminare di data discovery e light data quality.
Durante l’allineamento iniziale, lo stakeholder ha segnalato un problema di insoddisfazione cliente, ipotizzando un possibile collegamento con i tempi di consegna e con l’esperienza post-consegna. Tuttavia, non erano disponibili KPI aziendali già definiti, metriche operative strutturate o una causa secondaria confermata.
Per questo motivo, prima di definire uno Scope of Work definitivo e prima di iniziare l’analisi, è stato necessario verificare se il dataset fosse accessibile, strutturato, coerente e utilizzabile per costruire KPI misurabili.
La fase di data quality non è quindi partita come semplice pulizia tecnica, ma come controllo preliminare per capire:
- quali dati fossero disponibili;
- quali tabelle e colonne fossero rilevanti;
- quali relazioni potessero essere costruite;
- se i KPI necessari fossero computabili;
- se esistessero blocchi critici prima dell’analisi.

ENG:
This Data Quality Journal starts as a preliminary data discovery and light data quality phase.
During the initial alignment, the stakeholder reported a customer dissatisfaction issue, with a possible connection to delivery times and post-delivery customer experience. However, no predefined business KPIs, structured operational metrics, or confirmed secondary cause were available.
For this reason, before defining a final Scope of Work and before starting the analysis, it was necessary to verify whether the dataset was accessible, structured, consistent, and usable to build measurable KPIs.
Therefore, the data quality phase did not start as a simple technical cleaning activity, but as a preliminary check to understand:
- which data was available;
- which tables and columns were relevant;
- which relationships could be built;
- whether the required KPIs were computable;
- whether any critical blocking issues existed before the analysis.

CONTEXT

WHO:
The dataset comes from the OLIST Brazilian E-Commerce dataset, provided through Kaggle. In the project simulation, the business stakeholder is the Olist Operation Manager.
WHAT:
The dataset represents e-commerce marketplace operations, including customers, sellers, orders, order items, payments, reviews, products, geolocation data, and product category translations.
WHERE:
The original files are CSV files downloaded from Kaggle and imported into a local PostgreSQL database named "olist", under the "public" schema.
WHEN:
The main transactional data covers the available OLIST order period, mainly from 2016 to 2018. Static reference tables, such as products, sellers, customers, geolocation, and category translations, do not represent a transaction period by themselves.
WHY:
The data is used to investigate customer dissatisfaction, with a focus on delivery performance, delivery expectation gaps, customer reviews, and possible operational patterns linked to negative customer experience.
HOW:
The data was downloaded through Python using kagglehub, copied into the project directory, imported into PostgreSQL using COPY / copy_expert, and then validated through Python and SQL data quality checks.

FILE TYPE AND FILE SIZE ASSESSMENT

File type:
The source files are CSV files.
Main tools used:
Python, PostgreSQL, SQL, pandas, psycopg2, SQLAlchemy, DBeaver.
Reason:
The dataset is composed of multiple CSV files with relational structure. PostgreSQL was selected as the main working environment because it allows efficient bulk loading, structured validation, joins, data type conversion, and scalable SQL analysis.
File size assessment:
The copied dataset size is approximately 120 MB. During the initial workflow, a heavier import approach using pandas/to_sql was considered inefficient for the operational context, so PostgreSQL COPY / copy_expert was used instead.
Tool decision:
Excel was not selected as the main tool because the dataset is relational and contains multiple tables.
Python was used for automation, file handling, import orchestration, and dynamic checks.
PostgreSQL was used as the source of truth for validation, data type conversion, logical checks, KPI readiness, and future analysis.
Decision:
Python + PostgreSQL is the appropriate setup for this dataset.

LIMITATIONS
incomplete_data:
A small number of delivered orders are not fully computable for delivery KPIs due to missing required delivery date fields.
Delivery KPIs are computable on 96,470 delivered orders out of 96,478.
Delivery-review relationship KPIs are computable on 96,353 delivered orders linked to reviews out of 96,361.
misaligned_definitions:
No official business KPIs, internal Service Level Agreement. definitions, or dissatisfaction categories were provided by the stakeholder.
The analysis uses dataset-based definitions for delivery delay, delivery expectation gap, review score, and negative review rate.
data_gaps:
Customer support tickets, complaints, refund requests, post-purchase communications, and internal customer service records are not available.
Review text is available but not analyzed in depth during this phase.
External logistics or carrier data is not available.
reliability_issues:
City fields contain spelling variations, accent differences, and inconsistent formats.
The geolocation table contains duplicated groups and multiple records for some ZIP code prefixes.
Some temporal inconsistencies were detected in order delivery dates.
Some payment/order total differences exist and were considered plausible in the marketplace context, but not fully reconciled as accounting records.
cleaning_limitations:
No destructive cleaning was applied.
No rows were deleted.
No original values were overwritten.
Anomalies were flagged and documented, while original data was preserved.
